## About

SANA-WM Bench is NVIDIA's public benchmark for minute-scale, camera-controlled world-model video generation, released with the Sana project. It evaluates 80 fixed first-frame scenes under two 60-second camera trajectory splits, `simple_60s` and `hard_60s`. Each trajectory is 961 frames at 16 FPS. A model receives the first frame, a text prompt, and a full camera trajectory, and must generate the 60-second video that follows that trajectory.

WorldFoundry integrates the benchmark as an in-tree composite evaluator: the benchmark-specific layout, prompt binding, revisit-pair protocol, temporal-window aggregation, and scorecard contract live in this repository. The runner deliberately reuses WorldFoundry's resident VBench and Pi3 surfaces instead of executing an NVlabs/Sana checkout at evaluation time.

Official references:

- Official repo: [NVlabs/Sana](https://github.com/NVlabs/Sana) (evaluator under `tools/metrics/sana_wm`, pinned head `6298508fcb511762a11c42cff45b2fc9fd930325`)
- Paper: [arXiv:2605.15178](https://arxiv.org/abs/2605.15178)
- Documentation: [nvlabs.github.io/Sana/docs/sana-wm-bench](https://nvlabs.github.io/Sana/docs/sana-wm-bench/)
- Dataset: [Efficient-Large-Model/SANA-WM-Bench](https://huggingface.co/datasets/Efficient-Large-Model/SANA-WM-Bench) (public, not gated)

## In-tree paths

- Runner entry point: `worldfoundry/evaluation/tasks/execution/runners/sana_wm_bench/run_sana_wm_bench_official_runner.py`
- Evaluator implementation: `worldfoundry/evaluation/tasks/execution/runners/sana_wm_bench/sana_wm_bench_official_impl.py`
- Generation-request materializer: `worldfoundry/evaluation/tasks/execution/runners/sana_wm_bench/sana_wm_bench_prompts.py`
- Catalog entry: `worldfoundry/data/benchmarks/catalog/video/sana-wm-bench.yaml`
- Task YAML: `worldfoundry/data/benchmarks/tasks/external/sana-wm-bench.yaml`
- Runtime profile: `worldfoundry/data/benchmarks/runtime_profiles/official/sana-wm-bench.yaml`

There is no `worldfoundry/data/benchmarks/assets/sana-wm-bench` directory; all benchmark data comes from the public Hugging Face dataset.

The VBench dimensions are computed by the shared in-tree VBench runtime at `worldfoundry/evaluation/tasks/execution/runners/vbench/runtime/vbench`, with the official dimension weights and normalization bounds imported from `vbench_official_impl.py`. This is a reuse of the shared scorer, not a second VBench implementation. LPIPS uses the standard `lpips` package (AlexNet backbone); revisit SSIM requires `scipy`.

## Evaluation protocol and data layout

Download the public dataset:

```bash
hf download Efficient-Large-Model/SANA-WM-Bench \
  --repo-type dataset \
  --local-dir /path/to/datasets/SANA-WM-Bench
```

The two logical splits map to these dataset directories:

| Split | Dataset directory |
| --- | --- |
| `simple_60s` | `benchmark_v2_smooth_60s/` |
| `hard_60s` | `benchmark_v2_hard_60s/` |

Expected dataset layout per split:

```text
/path/to/datasets/SANA-WM-Bench/
  images/<scene_id>.png                                  # 80 fixed first frames (shared)
  benchmark_v2_smooth_60s/
    sanawm_export_v2/run_manifest.jsonl                  # 80 scene rows: id, prompt, image_path, camera_path
    sanawm_export_v2/<scene_id>.npz                      # c2w camera trajectory + embedded intrinsics
    scene_trajectories_v2.json                           # revisit evaluation_pairs metadata
  benchmark_v2_hard_60s/
    ... same structure ...
```

Each manifest row binds a scene id to a prompt, a first-frame image, and a camera trajectory. The canonical scale is 80 scenes per split, 961 frames per scene, 16 FPS. With `--limit` unset the runner is strict and fails if a split does not contain exactly 80 scenes or if any scene asset is missing.

Generated videos must be named `<scene_id>_generated.mp4`. The runner accepts either a flat directory or one subdirectory per split:

```text
results/my_method/
  simple_60s/
    <scene_id>_generated.mp4
    ...
  hard_60s/
    <scene_id>_generated.mp4
    ...
```

Any filename that does not end with `_generated.mp4` is ignored. Per-split coverage (expected vs. found videos) is recorded in the scorecard.

## Metrics

Scorecard leaderboard keys are `<split>.<metric_id>`, e.g. `simple_60s.vbench_overall`. There is no single cross-split aggregate; report both splits.

| Metric id | Meaning | Direction |
| --- | --- | --- |
| `vbench_overall` | Weighted VBench quality score over 7 quality dimensions, scaled to 0-100. Primary per-split key. | higher |
| `vbench_total_score` | Diagnostic 4:1 quality/semantic blend of all 9 VBench dimensions. | higher |
| `revisit_psnr` | PSNR between revisit frame pairs from `scene_trajectories_v2.json`. | higher |
| `revisit_ssim` | SSIM between revisit frame pairs. | higher |
| `revisit_lpips` | LPIPS between revisit frame pairs (only with `--revisit-lpips`). | lower |
| `rot_err_deg` | Camera rotation error in degrees, from imported Pi3 pose results. | lower |
| `trans_err_rel` | Relative camera translation error, from imported Pi3 pose results. | lower |
| `cam_mc_rel` | Relative camera motion-consistency error, from imported Pi3 pose results. | lower |
| `delta_iq` | Temporal imaging-quality degradation: first-window minus last-window VBench `imaging_quality`. | lower |

The nine VBench dimensions used are `subject_consistency`, `background_consistency`, `temporal_flickering`, `motion_smoothness`, `dynamic_degree`, `aesthetic_quality`, `imaging_quality`, `overall_consistency`, and `temporal_style`. Temporal degradation re-runs `subject_consistency`, `background_consistency`, `temporal_flickering`, and `imaging_quality` on fixed-length windows (default 10 seconds, `--window-seconds`).

## Data and checkpoint preparation

```bash
cd /path/to/WorldFoundry
export WORLDFOUNDRY_SANA_WM_BENCH_DATASET_ROOT=/path/to/datasets/SANA-WM-Bench
export WORLDFOUNDRY_GENERATED_ARTIFACT_DIR=/path/to/results/my_method
export WORLDFOUNDRY_BENCHMARK_OUTPUT_DIR=tmp/sana-wm-bench   # optional --output-dir default
```

VBench dimension checkpoints are resolved by the shared in-tree VBench runtime; see the [VBench page](/docs/evaluation/benchmark-hub/vbench) for weight staging. Revisit LPIPS downloads the AlexNet LPIPS weights through the `lpips` package on first use.

Camera-pose metrics are import-only in this runner: run Pi3 pose estimation as its own distributed GPU stage, then place its per-split `eval_poses.json` next to the generated videos (`<generated_dir>/<split>/eval_poses.json`) or pass `--pose-results-path`. Expected keys per scene row are `RotErr` (with optional `RotErr_unit: rad`), `TransErr_rel`, and `CamMC_rel`.

## Generate candidate videos

`sana_wm_bench_prompts.py` materializes one generation request per manifest row with the prompt, first frame, camera trajectory (`c2w_npz` with embedded intrinsics), `fps=16`, and `num_frames=961`, and expects the output artifact `<scene_id>_generated.mp4`. Model-side generation runs through the WorldFoundry generation workflow; the copy helper enforces the exact official filename layout.

## Run official scoring

Through the unified benchmark entry (the dataset root is read from `WORLDFOUNDRY_SANA_WM_BENCH_DATASET_ROOT`):

```bash
worldfoundry-eval zoo benchmark-run \
  --benchmark-id sana-wm-bench \
  --mode official-run \
  --generated-artifact-dir "${WORLDFOUNDRY_GENERATED_ARTIFACT_DIR}" \
  --env WORLDFOUNDRY_SANA_WM_BENCH_DATASET_ROOT="${WORLDFOUNDRY_SANA_WM_BENCH_DATASET_ROOT}" \
  --output-dir tmp/sana-wm-bench/official-run \
  --json
```

Use the direct runner for arguments not surfaced by the public wrapper, such as `--split`, `--metrics`, `--limit`, `--max-pairs`, `--revisit-lpips`, `--pose-results-path`, `--device`, and `--window-seconds`:

```bash
PYTHONPATH=. "${WORLDFOUNDRY_UNIFIED_PYTHON:-python}" \
  worldfoundry/evaluation/tasks/execution/runners/sana_wm_bench/run_sana_wm_bench_official_runner.py \
  --run-official \
  --dataset-root "${WORLDFOUNDRY_SANA_WM_BENCH_DATASET_ROOT}" \
  --generated-video-dir "${WORLDFOUNDRY_GENERATED_ARTIFACT_DIR}" \
  --split all \
  --metrics vbench,revisit,temporal,camera \
  --revisit-lpips \
  --device cuda \
  --output-dir tmp/sana-wm-bench/official-run \
  --json
```

`--split` accepts `all`, `simple_60s`, or `hard_60s` (aliases `simple`/`hard`). `--metrics` is a comma-separated subset of `vbench,revisit,temporal,camera`. `--limit N` scores only the first N scenes for a bounded smoke run and disables the strict 80-scene check.

## Import existing results

If you already have an aggregate result JSON in the runner's record schema (`records: [{split, vbench: {quality, total}, revisit: {psnr, ssim, lpips}, camera: {rot_err_deg, trans_err_rel, cam_mc_rel}, temporal: {imaging_quality_drop}}]`), import it without executing any evaluator:

```bash
worldfoundry-eval zoo benchmark-run \
  --benchmark-id sana-wm-bench \
  --mode official-validation \
  --official-results-path /path/to/aggregate_results.json \
  --generated-artifact-dir "${WORLDFOUNDRY_GENERATED_ARTIFACT_DIR}" \
  --output-dir tmp/sana-wm-bench/official-validation \
  --json
```

The direct runner accepts the same file via `--official-results-path`. `--run-fixture` writes a deterministic placeholder record for wiring tests only; never report fixture numbers.

## Outputs

The run writes under `--output-dir`:

- `scorecard.json`: WorldFoundry scorecard with per-split metrics, `<split>.<metric_id>` leaderboard keys, and per-split video coverage.
- `raw_metric_table.jsonl`: one row per metric per split, with `higher_is_better` and availability flags.
- `eval/<split>/vbench/`: raw VBench per-dimension result JSON files.
- `eval/<split>/revisit_consistency.json`: per-scene revisit pairs and PSNR/SSIM/LPIPS summaries.
- `eval/<split>/temporal_degradation.json` and `eval/<split>/temporal/windows/`: per-window clips and VBench trend data behind `delta_iq`.

## What this cannot claim

- A local scorecard is not an NVIDIA leaderboard submission; the scorecard hard-codes `leaderboard_valid: false`.
- Full 80-scene, two-split numerical parity against the upstream evaluator has not been run in this checkout (`official_benchmark_verified: false`); only bounded fixture wiring is verified.
- Fresh Pi3 camera-pose estimation is intentionally a separate distributed GPU stage. This runner only imports its `eval_poses.json`; camera metrics are absent unless you supply that file.
- `--run-fixture` and result imports produce normalized scorecards, not official runtime evidence.
- Running VBench, revisit, and temporal metrics requires a CUDA GPU plus VBench weights; nothing on this page claims those runs were executed here.
