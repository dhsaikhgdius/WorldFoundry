WorldFoundry is open-source infrastructure for running and evaluating world models. It is not another model architecture. It connects model discovery, runtime preparation, inference, artifact inspection, benchmark execution, and evidence reporting into a single workflow that spans video, 3D/4D, interactive-world, and embodied systems:

> Discover a model, prepare its runtime and assets, generate inspectable artifacts, evaluate those artifacts, and preserve the result as reviewable evidence.

That distinction matters. A model listed in a catalog is not a model with a working runtime. A convincing demo is not benchmark evidence. A score that imported cleanly is not leaderboard parity. WorldFoundry keeps those states separate and visible.

The problem it addresses is practical. Every upstream project produces something worth using, but each arrives with its own environments, checkpoints, inputs, launch commands, output layouts, and evaluation protocols. WorldFoundry preserves those native differences and standardizes the boundaries around them.

## The problem it solves

World-model projects usually arrive as independent repositories. Each makes its own choices about environments, checkpoints, input schemas, launch scripts, output layouts, preview tools, and evaluation code. A team that wants to compare several systems ends up rebuilding the same integration layer for every model.

The fragmentation starts at discovery. The same model may go by a paper name, a repository name, a checkpoint name, or a local folder. WorldFoundry gives models and benchmarks stable IDs and declarative manifests, so the source, intended capability, runtime binding, required assets, and known blockers can all be inspected before anything expensive runs.

It continues at execution. Rather than scattering checkpoints and datasets wherever an upstream script happens to expect them, WorldFoundry defines reusable local asset roots and model-specific runtime profiles. Pipelines and operators keep native model differences explicit while presenting one consistent request, result, and artifact boundary to the rest of the system.

It ends at evaluation, where evidence is easiest to lose. Videos, meshes, actions, and traces should not disappear into ad-hoc folders or one-off notebooks. WorldFoundry records what was requested, what ran, what was produced, how it was scored, which samples were covered, and which conditions still block an official claim.

The goal is not to hide every model difference behind one small API. It is to keep those differences in the layer where they belong, and to make the end-to-end research workflow consistent.

## How the project works

<WorldFoundryWorkflow />

The central boundary is the **artifact**. A model runner turns a normalized request into a result: videos, geometry, action traces, or other outputs. A benchmark runner consumes those outputs and produces metrics and evidence. Because of that separation, one model output can be inspected, reused, or scored by several compatible benchmarks without coupling the model implementation to evaluator internals.

Catalogs form the control plane around that boundary. They describe what exists, where it came from, what it needs, how it can be dispatched, and what evidence supports its current readiness. TUI, CLI, Studio, Python, and MCP are five ways to operate the same underlying system, not five separate implementations.

### A concrete run: Matrix-Game 2

For a first `matrix-game-2` run, let the catalog and local-asset checks confirm which model is selected and whether its checkpoint is ready, then generate one small result:

```bash
bash scripts/inference/prepare_model_infer.sh matrix-game-2 --download
python -m worldfoundry.evaluation zoo model-download \
  --model-id matrix-game-2 --check-local --json

bash scripts/inference/test_nav_video_gen.sh matrix-game-2 \
  --output-dir tmp/matrix_game2_first_run
```

The last command runs the model on action-conditioned input and writes the video and its run records to the chosen directory. What that justifies is one claim: this configuration produced an inspectable artifact. Motion and continuity can be reviewed in Studio or a local player, and compatible metrics can consume the artifact. A single video still does not establish that a complete benchmark ran — which is why WorldFoundry separates generation, inspection, scoring, and eligibility.
