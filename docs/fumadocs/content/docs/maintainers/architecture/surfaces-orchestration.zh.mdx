## 本层职责

TUI、CLI、Studio、Python、MCP 是操作同一系统的不同方式，都不承载模型推理或 benchmark 打分。它们的任务是把用户意图转换为执行层已理解的某一种 request 类型，并展示结果。本页覆盖两个非 UI 入口 —— CLI/TUI 与 MCP —— 以及把意图编译为可运行 plan 的编排服务。

request 产生之后落到哪里，先读 [工作流](/zh/docs/maintainers/architecture/workflow)。实际执行的 delegate runner 见 [评测核心](/zh/docs/maintainers/architecture/evaluation-core)。

## CLI 与 TUI

控制台入口是 `worldfoundry/cli/main.py:1580` `main()`。它在 `cli/main.py:1091` 起构建子命令树：

- **`tui`** —— 启动引导式发现 TUI。TUI 在 `cli/tui.py`（`main` 在 `:131`），app、discovery、brand、icon 助手在 `cli/tui_*.py`。它驱动与 CLI 相同的 catalog 与编排调用，只是展示，不是第二套 runtime。
- **`evaluate`** —— 归一化输入、选择 run mode、返回一个 `EvaluateRunResult`。
- **`run`** —— 模型运行：解析 runner、生成、再打分。
- **`validate`** —— 不跑模型即校验 benchmark metadata 加载。
- **`embodied`** —— 具身评测子树（`run`、`serve`、`merge`、`plan`）。
- 另有 `zoo`、`preflight`、`dataset`、`tasks`、`reporting`、`model_run`、`plan_metric`、`mcp` 助手。

CLI 调度到编排服务，不直接 import pipeline 文件或算 metric。保持这一点，才能在不重新实现生成、artifact 物化或打分的前提下新增界面。

## MCP

MCP server 把 catalog、run 生命周期、metric、readiness 暴露为工具，让 agent 驱动同一工作流。它是复用同一套契约的薄壳，不含私有模型代码。

- 入口：`mcp/__init__.py:30` `main()`；server 构造在 `mcp/server.py`（`build_server` `:41`、`run_server` `:52`）。
- 工具经 `mcp/tools/registration.py:47` `register_tools` 注册，把每个 payload 绑定为 `@mcp.tool()`。
- 工具 payload 按职责分组，而非按模型：`discovery`（list/get model、benchmark、task）、`runs`（preview、evaluate、status、result、samples、cancel）、`metrics`（list、show）、`readiness`（benchmark dataset 检查）、`studio`（workspace 推理）、`context`（`MCPToolContext`）。

因为每个工具都经同一 catalog 与编排服务解析，MCP 驱动的 run 与 CLI 驱动的 run 产出相同的 artifact 与 scorecard。

## 编排服务

编排服务是界面与执行之间唯一的编译边界，位于 `evaluation/tasks/execution/orchestration/service.py`。它校验五个 intent dataclass 之一，返回执行层可运行的 `PreparedEvaluation`。

| Intent | 文件:行 | 编译到 |
| --- | --- | --- |
| `ModelBenchmarkIntent` | `service.py:60` | `ModelBenchmarkRunRequest`（model + benchmark） |
| `ScoreArtifactsIntent` | `service.py:85` | 为已有 artifact 打分 |
| `GenerateAndScoreIntent` | `service.py:101` | 先生成再打分 |
| `ScoreResultsIntent` | `service.py:125` | 为磁盘上的 result 打分 |
| `ReproduceIntent` | `service.py:139` | 复现 profile |

每个 intent 有对应的 `_prepare_*` 函数（`service.py:421`–`:649`）。公共入口是 `prepare_evaluation(intent)`（`service.py:759`）与 `execute_prepared_evaluation(prepared)`（`service.py:775`）。界面的职责是产出其中一个 intent，不得重复实现生成、调度或 metric 执行。

## 三个规划边界

WorldFoundry 保持三种规划类型相互独立。不要用第四种 recipe executor 包裹它们。

| 边界 | 文件:行 | 职责 |
| --- | --- | --- |
| `PreparedEvaluation` | `service.py:198` | 面向用户的编译结果：preflight 诊断、协议保真策略、由 generation/data/evaluation/runtime/reference 溯源推导出的 claim 等级。 |
| `RunPlan` | `orchestration/plan.py:113` | 单个生成/评测 stage 的低层 plan；带指纹，保证可复现重跑与缓存复用。 |
| `EvaluateRunRequest` / `ModelBenchmarkRunRequest` | `orchestration/evaluate.py:37` / `orchestration/model_benchmark.py:47` | delegate runner 实际消费的 request 类型。 |

调用方标志只能*收窄* claim 等级，绝不能把诊断型 run 提升为官方 run。`score_valid` 记录 evaluator 是否产出可用分数；`leaderboard_valid` 另需可比溯源与 benchmark-runner 证据。claim 等级如何流入 scorecard 见 [评测核心](/zh/docs/maintainers/architecture/evaluation-core)。
