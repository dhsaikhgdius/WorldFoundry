title: 包含什么
description: WorldFoundry 的 catalog、runtime、使用界面、评测工具、输出与支持状态。
---

WorldFoundry 不只是论文列表，也不只是评测 wrapper。仓库包含 catalog 层、执行层、检查层与证据层。每一层都可以单独使用，但它们被设计成一条完整工作流。

## Catalog：先知道系统中有什么

**Model Zoo** 为世界模型系统分配稳定 ID 与 alias。一个模型 manifest 可以记录任务、上游来源、checkpoint 引用、variant、runtime binding、安装 profile、硬件预期、验证说明与已知 blocker。仓库当前收录了 200 多个模型条目，但这个数字描述的是 catalog 覆盖，不是统一的 runtime 成熟度。

这些条目分布在五个操作家族中。视频目录覆盖文本、图像与视频条件生成、编辑、动画和音视频系统；世界模型目录关注交互世界、导航、动作或相机条件生成与 simulator；3D/4D 目录包含重建、深度、点云、scene 表征与动态几何；VLA/VA/WAM 目录覆盖具身 policy 与 world-action 系统；托管 API 目录则对应权重从不在本地加载的 provider-backed 系统。

**Benchmark Zoo** 为评测 protocol 提供同样的声明层。当前 60 多个 manifest 覆盖生成视频质量、物理与动态一致性、相机和 3D/4D 行为、世界模型能力、安全、记忆与具身控制。Benchmark manifest 可以声明 dataset、生成输出 layout、metric 资产、官方命令、normalizer、runtime profile、eligibility 条件与 blocker。

下载任何资产之前，先查询 catalog：

```bash
worldfoundry-eval zoo models --json
worldfoundry-eval zoo benchmarks --json
worldfoundry-eval zoo model-show --model-id <model-id> --include-manifest --json
worldfoundry-eval zoo benchmark-show --benchmark-id <benchmark-id> --json
```

模型的详细索引见[模型目录](/zh/docs/guides/supported-models)，benchmark 的真实要求与当前执行路径见 [Benchmark Hub](/zh/docs/evaluation/benchmark-hub)。

## Runtime：把声明变成实际工作

模型执行由树内 pipeline 与 operator、本地 checkpoint loader、托管 API adapter、subprocess launcher 和独立环境 dispatch 共同实现。Pipeline 尽量贴近模型的原生实现，operator 则把该实现适配到 WorldFoundry 的 request 与 artifact。

因此 WorldFoundry 可以容纳输入输出差异很大的模型，而不必把它们压平成失真的最小公共接口。文本生成视频模型可以公开 prompt 与采样控制，camera-conditioned 模型可以接收 trajectory，3D 系统可以输出几何，robot policy 可以产出动作或 trace。它们的原生差异保持可见，而执行状态与输出会进入同一套报告系统。

有些 runtime 可以在统一环境中工作，另一些需要独立 conda profile、官方上游环境、simulator container 或 API 凭据。[环境配置](/zh/docs/reference/environments)解释 profile 的选择方式，[本地资产指南](/zh/docs/guides/local-assets)说明 checkpoint、dataset 与 metric 权重的位置。

## 使用界面：操作同一个核心的不同方式

六个入口共用同一套 catalog 与运行契约，区别只在于由谁驱动工作。

- **TUI** — 引导式入口。与 CLI 读取相同 manifest，帮助选择 ID，并可以在启动昂贵任务前先打印最终命令。
- **CLI** — 自动化界面。覆盖发现、资产检查、task 与 dataset 物化、run plan、推理与评测、reporting、比较、验证和机器可读 JSON 输出。
- **Studio** — 浏览器 workspace。提供模型感知的 job 表单、推理历史、gallery，以及面向媒体、几何、timeline、simulator 与交互模型输出的 visualizer。Job 会写出可持久化输出，之后仍可评测；结果不会困在 UI 里。
- **Python API** — 研究契约。向进程内研究代码公开 request、result、run、metric 与 reporting 类型。
- **MCP server** — agent 工具。为 agent-driven 工作流提供边界明确的发现与评测工具。
- **Shell helper** — 逃生口。为上游细节无法干净塞进通用命令的模型家族或环境保留。

## 评测：从 artifact 走到证据

评测核心可以给已有 result ledger 打分，可以让注册模型执行物化 request，可以运行一个 model × benchmark cell，也支持部分 resume/cache、run 比较与 suite 级报告。可复用 metric 与完整 benchmark protocol 分开维护，因此 scorer 可以用于兼容 artifact，而不会因此声称完整复现了官方 benchmark。

Benchmark integration 分阶段成熟。有些只提供 metadata 与 asset plan；有些可以归一化已有官方形态结果；有些公开树内 metric 或 official runner facade；更少的一部分拥有 bounded runtime evidence。只有 protocol 专属数据、覆盖率、凭据与 validation gate 同时满足时，才可能形成完整 leaderboard 资格。

这种分阶段模型是刻意设计的。它让有价值的 catalog 与 normalization 工作先进入仓库，同时不夸大当前可运行或官方支持的范围。

## 报告：一次 run 结束后还留下什么

WorldFoundry 把 run 目录当作研究记录，而不是一次性 cache。典型 run 会保留描述身份与配置的 manifest、记录实际请求了哪些 sample 或条件的 request ledger，以及包含逐样本状态、耗时、错误与 artifact 引用的 result ledger。

生成 artifact 可以是视频、frame、图像、几何、点云、trajectory、动作、trace 或结构化行。Metric summary 保留机器可读的聚合结果，`report.md` 与 `summary.json` 分别服务人工阅读和紧凑的程序读取，`scorecard.json` 则在分数之外加入覆盖率、provenance、blocker、validation 状态与 eligibility。

具体文件取决于 run mode 与 integration。共同契约是：不可用的工作必须保持不可用——scorecard 不能把缺失 dataset、跳过的 sample 或未验证的官方路径伪装成成功。

## 刻意不包含什么

WorldFoundry 不转发模型 checkpoint、受限权重、完整 benchmark 数据集、simulator 资产、API key、私有 endpoint，也不保存普通用户输出。它同样不会 vendor 每一套上游训练栈，也不保证任意 model × benchmark 组合都有意义。

这些边界让仓库保持可审查，并尊重上游许可。仓库内的代码只描述外部资产如何接入一次 run，并在资产缺失时如实报告；它不会静默下载或替换受保护资源。
